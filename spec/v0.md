# necro spec, version 0

A repo's house rules, each one a command that finds violations plus the words that teach whoever trips it, often an agent, what's wrong and what to do instead. `necro` runs the commands, keeps count, and prints the words. The conformance suite in `tests/conformance/` makes this spec executable.

Version 0 is a draft: any 0.x release of necro may break it. necro 1.0 freezes version 1.

## A rule

```yaml
# necro.yaml, at the repo root
version: 0
include: [necro/*.yaml, necro:rust] # optional: more files holding rules, and packs
disable: [rust/lossy-cast] # optional: pack rules to turn off
override: # optional: a pack rule's files, exclude and params, replaced
  rust/no-unwrap: { exclude: '^build\.rs$' }
exclude: ^tests/fixtures/ # optional: files the whole run leaves out
rules:
  no-print:
    command: necro grep '\bprint\s*\(' -- 'src/*.gd'
    message: Raw print call
    why: Print output bypasses the structured game log, so a stray print never carries a seq or side.
    fix: Log through GameLog.format_event, or push_error for real failures.
    details: { file: docs/rules/no-print.md } # optional
    examples: # optional
      bad: print(points)
      good: GameLog.format_event("banked", {"points": points})
```

| Key        | Required | Meaning                                                              |
| ---------- | -------- | -------------------------------------------------------------------- |
| `command`  | yes      | finds the violations: [Commands](#commands)                          |
| `message`  | yes      | what's wrong, one line                                               |
| `why`      | yes      | why the rule exists                                                  |
| `fix`      | yes      | what to do instead                                                   |
| `details`  | no       | the long form, for `necro --explain`                                 |
| `examples` | no       | `bad` and `good`, each a snippet or a list of them; both needed     |
| `files`    | no       | the files that make the rule run in a [narrowed run](#narrowed-runs) |
| `exclude`  | no       | files outside the rule: they never run it, and its hits there are dropped |
| `params`   | no       | named values for the command and the words: [Parameters](#parameters) |
| `autofix`  | no       | a command that fixes the rule's hits in place: [Fixes](#fixes)       |

- `message`, `why`, `fix` and `details` are each a string or `{file: <path>}`, a text or markdown file relative to the root, printed as is.
- `examples` are documentation: `--explain` shows them. necro doesn't run them.
- A rule's name is lowercase words joined by hyphens, unique across `necro.yaml` and its includes.
- `include` lists globs relative to the root, and [packs](#packs) as `necro:<pack>`; each file a glob matches holds only `rules:`. Unknown keys anywhere are errors.
- `disable` lists pack rules to turn off, and `override` maps a pack rule to its own `files`, `exclude` and `params`, both by the rule's full name ([Packs](#packs)).
- `files` and `exclude` take prek's form: a string is a regex, searched anywhere in the path (lookaround works), and `{glob: <glob or list>}` takes globs matched against the whole path, where `*` crosses `/`. Paths are relative to the root. `files` matters only to narrowed runs; `exclude` applies to every run: a hit in an excluded file is dropped before allows, so an allow there suppresses nothing.
- `exclude` at the top, in the same form, leaves files out of the whole run: every rule's hits there are dropped, necro reads no allows there, and a [narrowed run](#narrowed-runs) drops them from its files. It suits vendored code, fixtures, and files that quote rules or allows as data. Finders still search them; only the hits go.
- `baseline` names the snapshot file ([Baseline](#baseline)), relative to the root; the default is `necro.baseline.yaml`. A missing file means no baseline.

## Fixes

A rule can fix its own hits. `necro --fix` applies the fixes, checks again, and says what it changed and what it couldn't fix; a hook that runs it fails the commit until the fixed files are re-staged, as a formatter's does.

```yaml
trailing-space:
  command: necro grep --replace '' '[ \t]+$' -- '*.gd'
  …
gdformat:
  command: uv run --script necro/gdformat.py
  autofix: uv run gdformat {files}
  …
```

- **Fixable rules.** A rule whose command is a finder given a fix option (`necro grep --replace`, `necro agent-files claude-md` or `skill-link`) fixes through that finder: under `--fix`, necro adds `--write` and `--only-at <file>`, the hits to fix, as it adds `--files-from` in a narrowed run. Any other command names its fix in `autofix`, run as a command is ([Commands](#commands)): a word that is exactly `{files}` becomes one word per file with a hit to fix, and an `autofix` without that word is a config error, as is a parameter named `files`. A command that rewrites whole files may also change other hits in them.
- **What gets fixed:** the hits a run reports, after allows and the baseline, in the run's files. Allowed and baselined hits are left alone. Fixes run one rule at a time, in name order.
- **Then necro checks again** and reports what's left. The summary comes first: `necro: fixed <n> hits in <m> files (<rule> ×<k>, …); review and re-stage them. Why: necro --explain <rule>`, then, when hits are left, `necro: <n> hits can't be fixed automatically:` before them.
- **Exit** 1 when a fix changed a file or a hit is left, as a check run's would be otherwise.
- **Without `--fix`,** a full-format run that reports hits a fix could clear ends with `necro: <n> of <m> hits can be fixed automatically: necro --fix`. `--write-baseline` says how many of the entries it wrote are fixable: `necro: <n> of them can be fixed automatically; to keep them out of the baseline, run necro --fix first, then --write-baseline again`.

## Parameters

A rule can name values its command and words use, so a pack or an include can ship a default a repo changes without copying the rule.

```yaml
doc-length:
  command: uv run --script necro/docs.py --header {header} --item {item}
  params: { header: 10, item: 6 }
  message: a doc block is over its limit
  fix: cut it to {header} lines for the file header, {item} for any other doc.
```

- `params` maps each name (lowercase words joined by hyphens) to its default: a string, number or boolean, or a list of them.
- `{name}` stands for the value in `command`, `message`, `why`, `fix` and `details`. Only declared names are replaced, so other braces (`-{6,}` in a regex) stay as written.
- In `command`, replacing happens after the command is split into words, so a value is never re-split or read by a shell. A word that is exactly `{name}` for a list becomes one word per item; elsewhere in the command a list joins with commas (`a,b`), and in the words with a comma and a space. Values are used as written in the YAML (`10`, not `10.0`).
- `override: {<pack>/<rule>: {params: {<name>: <value>}}}` replaces the named values; the others keep their defaults. A name the rule doesn't declare, or a value of another kind than the default (a list for a number), is a config error.
- `--explain` shows each value, marked `(override)` when `necro.yaml` sets it.

## Packs

A pack is a set of rules built into necro and versioned with it, so the pin that picks necro's version picks the pack's too. `include: [necro:<pack>]` adds its rules.

- A pack rule's name is `<pack>/<rule>` (`rust/no-unwrap`) wherever a name appears: output, allows, the baseline, `--rule` and `--explain`. Repo rule names can't contain `/`, so the two never collide.
- `disable: [<pack>/<rule>…]` turns pack rules off. A disabled rule is gone, as if the pack didn't have it: an allow naming it suppresses nothing. A name that isn't a rule of an included pack is a config error. Allows and the baseline handle single hits; `disable` is for a rule a repo doesn't want at all.
- `override: {<pack>/<rule>: {files: …, exclude: …, params: …}}` replaces the rule's `files` or `exclude` (or adds one it lacks) with the repo's, and sets its [parameters](#parameters); nothing else about a pack rule changes. A name that isn't a rule of an included pack, or one `disable` turns off, is a config error. `--explain` and `--list` show the override.
- **Opt-in is a pack, not a switch.** Every rule of an included pack is on, minus `disable`. Rules a repo should choose, such as matters of taste, ship as a pack of their own (`necro:<lang>-style`), so `necro.yaml` alone shows what's on.
- An unknown pack is a config error. A pack's commands use only [finders](#finders) and the repo's own toolchain, and a rule that doesn't apply to the repo finds nothing.
- `--explain` names the pack a rule comes from.

### `necro:rust`

Rules for Rust code that default clippy doesn't enforce: no `unwrap()` or `expect()` outside tests, lint overrides as `#[expect]` with a reason, no `todo!`/`unimplemented!`/`dbg!`, a `SAFETY` comment on every `unsafe` block, no dropped `Result`, no truncating casts, and crate manifests on the current edition (parameter `edition`) with a `rust-version`. `necro --explain rust/<rule>` gives each one's words. It needs cargo and clippy.

### `necro:rust-style`

Opt-in house style for Rust, beside `necro:rust`: a `///` doc on every public item, a `//!` doc opening every file, doc blocks within a line limit (parameters `header`, 10, and `item`, 6), no decorative comment borders (`min-dashes`, 6), and no role-word type names (`role-words`: `Manager`, `Service`, …). It needs only git.

### `necro:agent-files`

The files coding agents read, where every harness finds them: beside each `AGENTS.md` a `CLAUDE.md` of only `@AGENTS.md` (`claude-md`, fixable; `claude-md-alone`), skills in `.agents/skills/<name>/` with a `.claude/skills/<name>` link to each (`skill-link`, fixable; `skill-misplaced`), skill frontmatter harnesses can load (`skill-frontmatter`), no instructions kept only in another harness's file (`other-instructions`), no pointer to a rule this repo doesn't have (`rule-reference`), and no necro skill from another necro version (`stale-skill`). It needs only git.

## Commands

- **Where it runs.** The root is the nearest folder at or above where necro starts (`-C <dir>` moves the start) that holds `necro.yaml`. The root must be inside a git work tree. A command runs with the root as its working folder, so a script is reached as `uv run --script necro/x.py`.
- **How it's read.** The command is split into words as a POSIX shell would (quotes, backslashes) and run directly: no shell, so no expansion, pipes or redirection. Anything more goes in a script.
- **What it prints.** Each non-empty stdout line is one violation, `path[:line[:col[-endcol]]][:label]`:
  - `path` is relative to the working folder and must name a file in it, or a symlink. With no `line`, the hit is the whole file.
  - `line` and `col` are 1-based; `col` counts Unicode code points; `endcol` is the last column of the span, inclusive.
  - `label`, the rest of the line after a `:` (one leading space dropped), is shown with the hit. `necro grep` prints the matched text there.
  - necro takes positions as printed, so another tool's quirks stay its own: `git grep --column` counts bytes, and with `-o` misplaces the second and later matches on a line.
- **Exit codes.** 0 and 1 are normal (grep exits 1 when nothing matches). Anything else, a line that doesn't parse, or a path that isn't a file is a check error, shown with the last 20 lines of the command's stderr.
- **Runtime.** A command may rely on git and on the repo's own development toolchain; nothing else is guaranteed. If its program isn't on `PATH`, that's a setup error naming the rule and the program. necro puts its own folder first on the command's `PATH`, so `necro grep` and the other [finders](#finders) run as the same necro. It drops `GIT_DIR` and `GIT_WORK_TREE`, which git sets for hooks in a worktree, so git finds the repo from the root as it would in a plain checkout. Python scripts run best as `uv run --script <file>` with their Python and dependencies declared inline (PEP 723).
- **Time.** A command runs until it exits; necro never kills it. Past 60 seconds, necro prints `necro: still running after 60 s: <rule>` on stderr, once for each rule still running, and keeps waiting.

## Finders

necro bundles finders for common searches. A finder is an ordinary command, not a special case: `necro <finder> [options] <args> [-- <pathspec>…]`. Every finder:

- prints its hits in the format of [Commands](#commands), paths relative to the working folder, sorted by path, line and column;
- exits 0 whether or not it found anything, and 2 on a usage error, with `necro: <finder>: <what>` on stderr, or when a tool it runs fails, with that tool's errors.

A file finder (`grep`, `rust-docs`) looks at the tracked files matching the pathspecs, read as `git grep` reads them (every tracked file under the working folder when there are none), and its `--glob`s; binary files are skipped. `--files-from <file>` (one path per line, relative to the working folder) keeps only the files it lists; a [narrowed run](#narrowed-runs) passes it.

A Cargo finder (`clippy`, `cargo-manifest`) takes no pathspecs. It looks at every Cargo workspace under the working folder: the one enclosing it, if any, and the workspace of each tracked `Cargo.toml` below it. It runs cargo in each workspace's folder, so that workspace's toolchain pin applies, and drops hits outside the working folder. With no workspace, it finds nothing.

More finders arrive in 0.x releases as adopters need them.

### `necro grep`

`necro grep [--skip-comments <marker>]… [--glob <glob>]… [--files-from <file>] [--replace <text> [--write] [--only-at <file>]] <regex> [-- <pathspec>…]`

- `<regex>` uses Rust's `regex` syntax plus lookaround (`(?<!…)`, `(?=…)`) and backreferences, as `fancy_regex` reads it, and matches within one line. A line where `fancy_regex` reaches its backtracking limit, which only patterns with lookaround or backreferences can, is an error naming the file and line; leave such files out with `--glob` or a pathspec. Every non-empty match is a hit, `path:line:col-endcol: <matched text>`, columns in code points.
- `--replace <text>` makes the hits fixable: each one's label becomes `replace with "<text>"`, with `$1` and `${name}` standing for the match's groups. `--write` then rewrites the files, replacing each match in place, and prints the hits it replaced; `--only-at <file>` (one `path:line:col` per line) limits it to matches starting there. Line endings are kept, and files that aren't valid UTF-8 are left alone.
- `--skip-comments <marker>` ignores the rest of a line from the first `<marker>` outside a `"…"` or `'…'` string. Give it once per marker (`--skip-comments '#'`, `--skip-comments //`).
- `--glob <glob>` keeps only files the glob matches, read as prek reads a `{glob: …}`: against the whole path relative to the working folder, with `*` crossing `/` (`--glob '*.rs'` takes every `.rs` file, `src/*` everything under `src/`), and `{a,b}` and `[…]` working. Give it once per glob. A leading `!` excludes instead (`--glob '!src/gen/*'`). A file must match one of the plain globs, if any, none of the `!` ones, and the pathspecs.

### `necro clippy`

`necro clippy [--tests] [--match <regex>] [--skip <regex>] <lint>…`

- Runs `cargo clippy --message-format=json` with a fixed set of clippy lints at warn, the ones `necro:rust` uses, so every rule shares one cached run per workspace (two with `--tests`). A lint outside the set is a usage error. Lints are named without the `clippy::` prefix.
- Builds into `necro/` inside the workspace's target folder, so it never invalidates the cache of the repo's own clippy runs. `necro --clean-cache` removes it ([CLI](#cli)).
- One cold build at a time per machine: until a workspace has a necro build for the mode (plain or `--tests`), a `necro clippy` waits while another cold one runs cargo, so the rules of one run, or two repos' hooks, build one after another and a first run takes one build's memory. Warm runs don't wait.
- A hit is the primary span of a diagnostic from one of the given lints, followed out of macro expansions to the repo's code: `path:line:col[-endcol]: <clippy's message>`. Two hits on one line are one, at the leftmost column.
- Test code is skipped: without `--tests`, test targets and `#[cfg(test)]` code aren't built. `--tests` adds them.
- Each crate is checked with its default features, as a plain `cargo clippy` would; code behind other features isn't seen.
- `--match` keeps, and `--skip` drops, hits whose span's text matches the regex.

### `necro cargo-manifest`

`necro cargo-manifest [--edition <year>]`

- Reads `cargo metadata` for each workspace (so `edition.workspace = true` resolves) and checks each member whose manifest is under the working folder.
- A member on an edition older than `--edition` (default 2024) is a hit at its `edition` line (`edition.workspace = true` included), or the whole manifest when it has none (cargo then defaults to 2015): `<manifest>:<line>:1: <name> is on edition <edition>`.
- A publishable member (`publish` isn't `false`) with no `rust-version` is a whole-file hit: `<manifest>: <name> is publishable with no rust-version`.

### `necro rust-docs`

`necro rust-docs [--files-from <file>] [--header <n>] [--item <n>] (missing|module|length) [-- <pathspec>…]`

Reads tracked `.rs` files line by line, without parsing Rust, and checks one thing about their doc comments. Pathspecs narrow the files as for `grep`.

- `missing`: each public item, a line starting `pub` (then `unsafe`, `async` or `const`, any of them) and `fn`, `struct`, `enum`, `trait`, `type`, `const`, `static` or `mod`, with no `///` line above it once blank and attribute lines are skipped: `path:line:col: <kind> <name>`, at `pub`. `pub(crate)` and other restricted visibility aren't public. Exempt: an item with a `#[test]` or `cfg(test)` attribute, one inside a `#[cfg(test)]` module, and `pub mod <name>;` whose file opens with `//!`.
- `module`: a non-empty file whose first line, past blank lines and inner attributes (`#![…]`), isn't a `//!` doc: `path:1:1: no //! module doc`.
- `length`: each run of doc lines (`///` or `//!`, not `////`) longer than its limit: `--header` (default 10) for a run holding `//!`, or one above a `struct`, `enum`, `trait`, `union` or `impl` past attributes; `--item` (default 6) for the rest. The hit is the run's first line: `path:line:1: doc block is <n> lines (limit <m>)`.

### `necro agent-files`

`necro agent-files [--write [--only-at <file>]] <check>`

Reads git's index under the working folder, so a symlink is judged as git records it (on a checkout that writes links as plain files, the file's text is the target). The files are judged together, so a narrowed run's `--files-from` is accepted and the whole folder checked.

- `claude-md`: an `AGENTS.md` with no `CLAUDE.md` beside it (`path: no CLAUDE.md beside it`, on the `AGENTS.md`), or a `CLAUDE.md` holding anything but `@AGENTS.md` and not a link to `AGENTS.md`.
- `claude-md-alone`: a `CLAUDE.md` with no `AGENTS.md` beside it.
- `skill-link`: a `.agents/skills/<name>/SKILL.md` without a `.claude/skills/<name>` symlink to `../../.agents/skills/<name>`, the hit on the `SKILL.md`.
- `skill-misplaced`: a real folder in `.claude/skills` (the hit on its `SKILL.md`), or a link there to no skill in `.agents/skills` (on the link).
- `skill-frontmatter`: a `SKILL.md` without `---` frontmatter, a `name` that is the folder's (lowercase words joined by hyphens, up to 64 characters), or a `description` up to 1024 characters.
- `other-instructions`: `.cursorrules`, `.windsurfrules`, `.clinerules`, `GEMINI.md` or `.github/copilot-instructions.md` holding text that doesn't mention `AGENTS.md`.
- `rule-reference`: in `AGENTS.md`, `CLAUDE.md` and `SKILL.md` files, a name after `necro --explain` or `necro --rule`, or a backticked `<pack>/<rule>` of a known pack, that isn't a rule `necro.yaml` turns on: `path:line:col-endcol: <name>`.
- `stale-skill`: a `SKILL.md` whose frontmatter `metadata: necro-version:` isn't the running necro's version.
- `--write` (with `claude-md` or `skill-link`) creates the missing `CLAUDE.md` (`@AGENTS.md`) or link, replacing a link that points elsewhere, and prints `path: fixed` for each; `--only-at <file>` limits it to the hits listed there.

## Allows

- An exception is a comment, in the file's own syntax, on the hit's line or the line above: `necro-allow <rule>: <reason>`. necro finds it on the raw line, so any comment style works. A whole-file hit takes an allow on line 1, or line 2 after a `#!` line.
- The reason runs to the line's end or the next `necro-allow`, with a trailing `*/`, `-->` or `;` dropped.
- Two built-in rules keep allows honest, with necro's own wording: `necro/allow-reason` (an allow without a reason) and `necro/unused-allow` (an allow that suppresses nothing, or names no rule). necro finds allows with `git grep` over the tracked files outside the top-level `exclude`, so an allow in a file no rule covers is reported as unused.

## Baseline

A snapshot of known hits, the ratchet: `necro` matches what's left after allows against it, so old violations stay silent while new ones fail.

- **File.** Flat YAML: `version: 1` plus an `entries:` list of `rule`, `path`, `fingerprint` and `line`, sorted by (rule, path, fingerprint); every run over the same hits writes byte-identical text.
- **Pipeline.** A run executes every rule's command (or one, with `--rule`), parses hits, applies allows, matches the rest against the snapshot, and prints. Finders never search the snapshot file: its fingerprints would match the content rules they came from.
- **Matching.** Entries group into buckets per (rule, path, fingerprint); each observed hit consumes one entry from its bucket. Leftover hits fail; leftover entries go stale. A `--rule` run matches only that rule's entries, so other rules' leftovers never warn as stale. The stored `line` is only a hint for humans and never part of the key, so moving a line doesn't relitigate it, and an over-count fails by exactly the excess.
- **Fingerprint.** A hit's fingerprint is its source line, trimmed, cut before the first valid `necro-allow` (whitespace after the marker, then a rule name); a whole-file hit's fingerprint is empty.
- **Regen.** `necro [-C <dir>] [--rule <name>] --write-baseline` snapshots the observed post-allow hits and confirms with `necro: wrote <path> (<n> entr(y|ies))`. A full regen replaces the snapshot; with `--rule`, only that rule's entries are replaced and every other rule's entries carry over (scoped regen merges, never wipes siblings). A missing snapshot is empty; a corrupt one is discarded and rebuilt: snapshot errors never block regen, and regen never deletes — no hits writes `entries: []`. Check or setup problems fail first (exit 2) and write nothing.
- **Builtins stay out.** `necro/*` diagnostics are never snapshotted and never matched, so a broken allow still fails right after regen.
- **Working off hits.** Whoever fixes hits, a person, an agent or `necro --fix`, works on the post-baseline failures only: silenced hits are done, stale entries are a human's regen cue, never work. A fix edits code (or deletes a dead allow); it never inserts `necro-allow` — an allow without a genuine fix still fails via the builtins — and never invokes `--write-baseline`, scoped or full. Regen is human-only, run over the full tree once the fix lands. Re-running is the check: all kept hits fixed means exit 0 with at most stale warnings; exit 2 is a hard stop, never a cue to regen to green.
- **Exit codes.** Snapshot-covered hits are silent and never fail. Stale entries warn on stderr — `necro: warning: <n> baseline entr(y|ies) no longer match(es); refresh with necro --write-baseline` — without failing. A snapshot that can't be read or parsed, or whose version isn't 1, is a setup error (exit 2).
- **Suppression wins.** Allows apply before the snapshot: an allowed hit never reaches it, and counts as used even when the snapshot would also cover it. An unused allow still errors (`necro/unused-allow`): matching is per (rule, path, fingerprint), and that diagnostic's rule is `necro/unused-allow`, not the rule the allow names.

## Narrowed runs

Given files (`necro [<file>…]`), a run checks what concerns them, the way a pre-commit hook does. pre-commit, or prek, picks the files: the staged ones for a commit, the pushed ones for pre-push, `--from-ref`/`--to-ref` in CI. With none, a run covers everything, as before.

- **Paths** are relative to the working folder, re-anchored to the root (`-C`), and may lie outside it (`../README.md`). Ones that aren't files, such as deleted ones, and ones the top-level `exclude` leaves out are dropped.
- **Rules.** A rule with `files` or `exclude` runs when a given file passes both (any file passes a missing `files`) and is skipped otherwise. A rule with neither always runs. A rule that runs runs in full, with its command as written, so a hit it causes in another file is still found, unless that file is excluded.
- **Finders.** necro's file finders (`necro grep`) search only the given files: necro passes them `--files-from`. The Cargo finders check whole workspaces as before.
- **Allows and baseline.** Every hit is reported, wherever it is. necro's allow checks (`necro/allow-reason`, `necro/unused-allow`) and stale baseline entries are judged only in the given files, since elsewhere a rule may not have looked.
- **Full runs still matter.** `--write-baseline` refuses file arguments, so a baseline always covers every file. A full run is what reports stale entries and allows outside the files a change touched.
- pre-commit splits very long file lists across several runs; a rule with neither key then runs once per run and repeats its hits. For a check of everything, run `necro` with no files.

## Messages

- **`full`** (default). Each rule's first hit: `error[<rule>]: <message>`, its location, the source line with the span underlined and the label beside it, then `why`, `fix` and the explain command. A repeat: `also at <location>`, its label, and `fix`. Past 4 repeats per rule, the rest are counted per file (`N more in <file>`). Hits sort by rule, path, line and column.
- **The underline.** `col-endcol` sets it; with only `col`, one caret. A label that is just the underlined text isn't repeated beside it; a repeat shows its label in parentheses after the location. Tabs show as 4 spaces, the underline moved to match. A whole-file hit shows no source line.
- `why` and `fix` wrap at 88 columns, continuation lines aligned.
- **The summary**, after the hits: counts per rule of errors; every allow (rule, location, reason). A clean run with nothing to list prints nothing.
- **`terse`**: one line per shown hit, `path:line:col: rule message` (`path: rule message` for a whole file), nothing else.
- Hits and the summary go to stdout; config, setup and check errors to stderr, as `necro: <kind> error: <where>: <what>`, config errors with `<file>:<line>:<col>: <key path>`.

## CLI

`necro [-C <dir>] [--format full|terse] [--rule <name>] [--fix] [<file>…]`, `necro [-C <dir>] --explain <rule>`, `necro [-C <dir>] --list`, `necro [-C <dir>] [--rule <name>] --write-baseline`, `necro [-C <dir>] --clean-cache`, `necro <finder> …` ([Finders](#finders)), `necro --version`.

- A run executes every rule's command (or one, with `--rule`), applies allows, matches the rest against the baseline, and prints. `--fix` then fixes what it can ([Fixes](#fixes)); `--explain`, `--list`, `--write-baseline` and `--clean-cache` refuse it. Given files, it's a [narrowed run](#narrowed-runs); `--explain`, `--list`, `--write-baseline` and `--clean-cache` refuse them.
- `--explain <rule>`: the message, `why`, `fix`, `details`, the examples, the command with its `files`, `exclude` and parameters (each marked `(override)` when `necro.yaml` sets it), and the pack it comes from. An unknown name is exit 2, with the rules listed.
- `--list`: every rule `necro.yaml` defines, includes or turns off, one per line sorted by name: the name, padded to the longest, two spaces, where it comes from (`necro.yaml`, an include file, or `necro:<pack>`), and for a pack rule `disabled` or `override: <keys>` after two more spaces. necro's own rules aren't listed.
- `--clean-cache`: removes the build folders the Cargo finders keep, `necro/` in the target folder of each workspace they would check from the root, printing `necro: removed <folder> (<size>)` for each, or `necro: no cache to clean`. It doesn't read `necro.yaml`, so it works on a broken config.
- Exit 0 when nothing fails, 1 when a rule has a hit or an allow is broken, 2 on a config, setup, check or usage error. Snapshot-covered hits never fail; stale entries warn on stderr only; a corrupt snapshot is a setup error on a check run (`--write-baseline` rebuilds it instead).

## Versioning

- `version` in `necro.yaml` is required. An engine reads the version it implements; another is exit 2, naming both versions.
- Breaking (needs a new version after 1.0): removing or renaming a key, changing what a command's output means, changing `terse` or exit codes, a stricter rule that makes a valid config invalid. Not breaking: new optional keys, and changes to `full` layout, which go in the changelog. A pack's rules change with necro's version, as its finders do: a new pack rule, or one that finds more, is a release note, not a new spec version.
