# necro spec, version 0

A repo's house rules, enforced by checks whose failure message teaches the rule and the fix to whoever trips it, often an agent. This spec covers the files, the config, the checks and their protocol, the messages and the CLI. `necro` implements it; the conformance suite in `conformance/` makes it executable, so another engine stays possible.

Version 0 is a draft: any 0.x release of necro may break it, so repos pin the hook's `rev`. necro 1.0 freezes version 1.

## Rule model

A repo writes every rule: its wording, scope and params are the repo's own. The engine supplies detection, as a ladder from cheapest to most capable:

1. `regex`: one line at a time, comments skipped.
2. `ast-grep`: syntax-aware patterns (arrives in a later 0.x).
3. A group script: any code, in the repo's own language, over the [check protocol](#check-protocol).

Built-in `engine.*` checks exist only where a common rule needs parsing the ladder handles badly. Use house rules where existing linters can't reach; a rule a linter already has belongs in that linter.

## Files

```
necro.yaml              # master: version, run scope, group list, defaults
necro/
  <group>.yaml          # one per group: guide + rules
  <group>.<ext>         # that group's checks, if it needs code (anything its command runs)
  fixtures/<group>/<rule>/{good,bad}/
  fixtures/<group>/good/  # optional: the good tree for rules that have none
necro.ratchet.tsv       # optional: counts for rules adopted over existing breakage
```

The root is the folder holding `necro.yaml`. It need not be the git root.

## Master

```yaml
version: 0
files: ["**/*"] # what a run looks at
ignores: ["necro/fixtures/**", "dist/**"]
groups: [necro, layer, docs] # must match necro/*.yaml exactly
defaults: # optional: any rule key, for every rule
  severity: error
languages: # optional: extend or override the language table
  .mdx: { like: .md }
```

- `version` and `groups` are required. An unlisted group file, or a listed group with no file, is a config error. Removing a group from the list turns it off.

## Groups and rules

```yaml
# necro/docs.yaml
guide: | # the group's long form: necro --explain docs
  How comments and docs are kept short in this repo …
files: ["src/**/*.rs"] # default scope for this group's rules
command: [python3, necro/docs.py] # only if the group has scripted checks
timeout: 60 # seconds for the whole process; default 60
rules:
  length: # the code is docs/length
    summary: "a comment block is over {{limit}} lines"
    why: say what the code can't, briefly; long comments go stale and hide the code
    help: "cut it to {{limit}} lines; longer reasoning goes in docs/"
    check: engine.comment-blocks
    params: { header: 10, block: 6 }
    where:
      - files: ["tests/**"]
        params: { block: 12 }
    explain: |
      ## What the rule says
      …
```

A group's file name is its code prefix and a rule's key is the rest: `<group>/<name>`, lowercase words joined by hyphens. Rule keys:

| Key                | Required | Meaning                                                          |
| ------------------ | -------- | ---------------------------------------------------------------- |
| `summary`          | yes      | what is wrong, one line                                          |
| `why`              | yes      | why the rule exists, one or two sentences                        |
| `help`             | yes      | a valid change, specific to the hit where possible               |
| `explain`          | yes      | markdown: what the rule says, why, bad and good, fair exceptions |
| `check`            | yes      | what detects it                                                  |
| `label`            | no       | short text under the underline                                   |
| `files`, `ignores` | no       | scope globs                                                      |
| `params`           | no       | values for the check's declared parameters                       |
| `where`            | no       | per-path overrides                                               |
| `severity`         | no       | `error` (default) or `experimental`                              |

A group may set `files`, `ignores`, `params` and `severity` as defaults for its rules.

- **One code per failure mode.** A check that finds several kinds of problem is several rules, each with its own `why`.
- **The `necro` group is required.** It holds the rules using `engine.allow-reason` and `engine.unused-allow`, so the repo words the engine's own allow errors. Without them, loading fails.

## Checks

`check` is one of:

- `{regex: <pattern>}`: matched per line; named groups become placeholder values. The dialect is Rust's `regex` crate: no lookaround or backreferences; `(?P<name>…)` and `(?<name>…)` both work. In a language the table knows, comments are blanked before matching and strings are kept; `in: line` beside `regex` matches the raw line.
- `engine.<name>`: a check built into the engine, configured by `params`.
- `<group>.<name>`: a check from that group's `command`, any group's.
- `{ast-grep: {language, rule, constraints}}`: reserved; a config error until ast-grep arrives.

A scripted or engine check declares:

- `scope`: `file` (sees only the files being checked) or `project` (always sees every file in the run's scope).
- `params`: each name's type (`string`, `number`, `boolean`, `string[]`, `map<string>`) and default.
- `values`: the placeholder names its hits may fill.

Values are facts about the hit (a token, a size) where possible. Templates have no conditionals: where the wording branches, the check returns only the phrase that varies, and lookup tables come in as `params`.

### Built-in checks

| Check | Scope | Params | Values | Hits |
| --- | --- | --- | --- | --- |
| `engine.comment-blocks` | file | `header`, `block` (numbers: max lines), `markers` (string[]: which comment markers count; default all of the language's) | `lines`, `limit` | a block over its limit, on its first line |
| `engine.require` | file | `pattern` (regex), `at` (`start` or `anywhere`; default `anywhere`) | | line 0 when the file lacks the pattern |
| `engine.doc-above` | file | `target` (regex for a line that needs a doc), `skip` (regex for lines allowed between, e.g. attributes), `markers` | named groups of `target` | the target line |
| `engine.allow-reason` | file | | `code` | an allow with no reason |
| `engine.unused-allow` | file | | `code` | an allow that suppresses nothing or names an unknown code |

A comment block is a run of consecutive comment lines using one marker, or one block comment. The header is the first block, when only what the language table allows comes before it. A Python docstring is a block; the module docstring is the header.

## Check protocol

A group with scripted checks names a `command`: an argv list, or a string split as a shell would split it (no shell runs).

- **One process per group per run.** It reads newline-delimited JSON on stdin and answers each message with one line on stdout, in order. The engine sends `describe`, validates the whole config, sends one `check` holding every job for the group, then closes stdin. `--explain` sends only `describe`.
- A **job** is one check with one resolved parameter set over its files. The engine sends every declared parameter, defaults included. Jobs carry no rule code. Identical (check, params, files) jobs from different rules are sent once.
- **cwd** is the root. **env** is inherited, plus `NECRO_PROTOCOL=1` and `NECRO_ROOT`. Paths both ways are root-relative with forward slashes. The engine sends paths, not contents.
- **stdout carries only protocol lines.** stderr is the script's log: shown (its last 20 lines) only when the process fails.
- Every message carries `protocol: 1`, separate from the spec version. A mismatch is a check error naming both.

```json
{"type": "describe", "protocol": 1}
{"protocol": 1, "checks": {"boundary": {"scope": "file", "values": ["specifier"],
  "params": {"forbid_paths": {"type": "string[]", "default": []}}}}}
{"type": "check", "protocol": 1, "jobs": [{"id": "1", "check": "boundary",
  "files": ["src/data/projects.ts"], "params": {"forbid_paths": ["src/pages/**"]}}]}
{"protocol": 1, "results": {"1": {"hits": [{"file": "src/data/projects.ts", "line": 1,
  "column": 1, "length": 41, "values": {"specifier": "../pages/index.astro"}}]}},
 "warnings": [], "errors": []}
```

- **Hits**: `line` is 1-based, or 0 for the whole file; `column` is 1-based (default 1) and `length` defaults to 0, both in Unicode code points. `values` hold only declared names, as strings or numbers. A value the wording uses must be present; send `""` for an intentionally empty phrase.
- **Warnings** (`job` optional) are shown in the summary and never fail a run. **Errors** (`{"job", "message"}`) mean the check couldn't run.
- **Check failure**: a nonzero exit, a timeout (the engine kills the process group), a line that isn't JSON, a missing result, an undeclared or missing value, a hit outside the job's files (a line-0 hit may name any file in scope), or a reported error. The engine prints `necro: check error: <group> (<command>): <what>` and the stderr tail, and other groups' hits still print. It fails the run (exit 2) when an `error` rule uses that check; when only `experimental` rules do, it's reported in the summary and the run doesn't fail. A failing check isn't a rule hit: allows and severity don't apply.

## Languages

The table drives comment blanking for `regex`, `engine.*` checks and the allow scan.

| Extensions | Line | Block | String quotes | Before the header |
| --- | --- | --- | --- | --- |
| `.ts .mts .cts .tsx .js .mjs .cjs .jsx` | `//` | `/* */` | double, single, backtick | shebang |
| `.astro` | `//` | `/* */`, `<!-- -->` | double, single, backtick | the `---` fence |
| `.css` | | `/* */` | `" '` | |
| `.py` | `#` | docstrings | `" ' """ '''` | shebang, coding line |
| `.rs` | `//`, `//!`, `///` | `/* */` | `"`, raw strings | |
| `.gd` | `#`, `##` | | `" ' """` | `@tool`, `class_name`, `extends` lines |
| `.md` | | `<!-- -->` | | YAML frontmatter |
| `.yaml .yml` | `#` | | `" '` | `---` |

- Another extension: `regex` runs on raw lines; `engine.*` checks scoped to it are a config error naming the extension.
- A repo's `languages` entry replaces a built-in one whole; `like` copies one: `.gdshader: { line: ["//"], block: [["/*", "*/"]], strings: ['"'] }`.

## Scope and parameters

- Each key resolves nearest first: `where` entry, rule, group, master `defaults`, the check's declared default. A level that sets a key replaces it; lists and params are never merged.
- A rule applies to files in the master's scope that match its effective `files` and not its `ignores`.
- `where` is a set of entries, each a `files`/`ignores` scope plus `params`, `severity` or wording (`summary`, `why`, `help`, `label`). An entry only narrows. A file matching two entries gets both; if both set one key, that's a config error naming the two entries and one such file, found at load from the run's files. Order doesn't matter.
- A `project` check runs once over every file in scope, so its `params` can't vary by `where`; its severity and wording still can, by the hit's file. A `file` check runs once per distinct parameter set.
- **Globs** follow globset: `*` stays within a path segment, `**` crosses them, `{a,b}` alternates, `*` matches dotfiles, and matching is case-sensitive.
- **Files**: in a git repo, tracked files plus untracked files that aren't ignored; outside git, a walk that respects `.gitignore`.
- **Loading validates everything** before any check runs: unknown keys, unknown or mistyped params, a placeholder that's neither a declared value nor a param, a `map` param in wording, a `check` that doesn't resolve, regexes that don't compile, invalid globs. Every config error is reported, sorted by file and line, as `necro: config error: <file>:<line>:<col>: <key path>: <message>`, with key paths like `rules.length.where[0].params.block`.

## Messages

- Placeholders `{{name}}` in `summary`, `why`, `help` and `label` take the hit's value first, then the effective param. Lists render comma-separated; numbers in their shortest form (`1`, not `1.0`).
- **`full`** (default), progressive. Every hit: code, summary, file:line:column, the source line with the span underlined. The first hit of a code also gets `label`, `why`, `help` and the explain command. A repeat gets `help`, plus summary or why only when the rendered text differs from what was shown; past 4 repeats per code, the rest are counted per file. Hits sort errors first, then by code, file and line. Lines wrap at 88 columns.
- Tabs in a shown line render as 4 spaces, with the underline moved to match; `length: 0` draws one caret; `\r` is stripped before matching and display. A line-0 hit shows no source line.
- When `necro` isn't on `PATH`, the explain line adds how to install the running version.
- **`terse`**: one line per hit, `file:line:column: code summary`. **`json`**: the resolved diagnostics, with a `version` field and a published schema.
- Diagnostics and the summary go to stdout; config and check errors to stderr. The summary lists every allow (code, file, reason), every warning, and experimental hits apart from errors. A clean run with nothing to list prints nothing.

```
error[t/clean]: src doesn't say bad
 --> src/a.ts:1:12
  |
1 | const a = "bad";
  |            ^^^ bad here
  |
  = why: Because.
  = help: drop bad
  = more: necro --explain t/clean

error[t/clean]: also at src/c.ts:1:10
   = help: drop bad

necro: 2 errors (t/clean ×2)
necro: allowed t/clean at src/d.ts:2: quoting the banned word
```

## CLI

`necro [files…] [--format full|terse|json] [--rule <code>] [--explain <code|group>]`, `necro test [--update]`, `necro --version`.

- No files: checks every file in scope. Given files: `file` checks see those, `project` checks still see everything. A given file out of scope or outside the root is skipped; a missing one is exit 2.
- `--rule <code>` runs only that rule (and the `necro` group's); scope still applies.
- `--explain <code>`: the rule's `explain`, its effective params per `where` entry, and its group's name. `--explain <group>`: the guide and each rule's code and summary. An unknown name is exit 2, with the codes listed on stderr.
- Exit 0 clean, 1 on any `error`-severity hit or a missing allow reason, 2 on a config error, check failure or usage error.

## Allows

- Inline, in a comment on the flagged line or the line above: `necro-allow <code>: <reason>`. A line-0 hit takes an allow on line 1, or on line 2 when line 1 is a shebang.
- A missing reason is an error (`necro/allow-reason`). An allow that suppresses nothing, or names an unknown code, is an error (`necro/unused-allow`); its rule's `ignores` exempt files that write allows as data.
- Prefer extending the interface over an allow. A rule that keeps needing allows is wrong: fix or drop it.

## Lifecycle

- A new rule starts `experimental`: reported, never fails. Promote it to `error` once its hits on the repo and its fixtures are right. There's no `warn`: agents and people skip warnings.
- The ratchet (`necro.ratchet.tsv`, `NECRO_RATCHET_INCREASE`) adopts a rule over existing breakage; it arrives in a later 0.x.
- Where rules come from: a correction given twice, to an agent or in review.

## Fixtures

- Per rule, `necro/fixtures/<group>/<rule>/good` must produce no hits and `bad` must, with `bad`'s full output kept as `expected.txt`. A rule without a `good` uses its group's shared `fixtures/<group>/good` if there is one. A rule without both is a test failure.
- `necro test` checks each fixture tree as if it were the repo: the repo's config, the fixture's files, paths relative to the tree (`bad/src/net/x.gd` is `src/net/x.gd`). It runs the rule plus the `necro` group's rules; the `necro` group's own fixtures run every rule. A snapshot mismatch shows a diff; `--update` rewrites `expected.txt`. The wording is the product, so snapshot changes go through review.
- Checks stay offline, deterministic and fast enough for a commit. The pre-commit hook checks the whole tree by default, and only the staged files when `pass_filenames` is set.

## Versioning

- `version` in `necro.yaml` is required. An engine reads a declared range of versions, normally the current one and the one before. A newer version exits 2 and says which rev to raise to; an older one outside the range exits 2 and points at the migration notes.
- **Breaking** (needs a new version after 1.0): removing or renaming a key, a value that changes meaning (resolution order, globs, the regex dialect, an `engine.*` check's params or values), a stricter rule that makes a valid config invalid, and changes to `terse`, `json` or exit codes. **Not breaking**: new optional keys, `engine.*` checks and languages, and changes to `full` layout, which go in the changelog; repos' snapshots catch them in review.
- JSON Schemas for `necro.yaml` and group files are generated from the engine's types and published per version, for editor validation.
