# necro spec, version 0

A repo's house rules, each one a command that finds violations plus the words that teach whoever trips it, often an agent, what's wrong and what to do instead. `necro` runs the commands, keeps count, and prints the words. The conformance suite in `tests/conformance/` makes this spec executable.

Version 0 is a draft: any 0.x release of necro may break it, so repos pin the hook's `rev`. necro 1.0 freezes version 1.

## A rule

```yaml
# necro.yaml, at the repo root
version: 0
include: [necro/*.yaml] # optional: more files holding rules
rules:
  no-print:
    command: necro grep '\bprint\s*\(' -- 'src/*.gd'
    message: Raw print call
    why: Print output bypasses the structured game log, so a stray print never carries a seq or side.
    fix: Log through GameLog.format_event, or push_error for real failures.
    details: { file: docs/rules/no-print.md } # optional
    examples: # optional
      bad: print(points)
      good: GameLog.format_event("banked", {"points": points})
```

| Key        | Required | Meaning                                                              |
| ---------- | -------- | -------------------------------------------------------------------- |
| `command`  | yes      | finds the violations: [Commands](#commands)                          |
| `message`  | yes      | what's wrong, one line                                               |
| `why`      | yes      | why the rule exists                                                  |
| `fix`      | yes      | what to do instead                                                   |
| `details`  | no       | the long form, for `necro --explain`                                 |
| `examples` | no       | `bad` and `good`, each a snippet or a list of them; both needed     |

- `message`, `why`, `fix` and `details` are each a string or `{file: <path>}`, a text or markdown file relative to the root, printed as is.
- `examples` are documentation: `--explain` shows them. necro doesn't run them.
- A rule's name is lowercase words joined by hyphens, unique across `necro.yaml` and its includes.
- `include` lists globs relative to the root; each matching file holds only `rules:`. Unknown keys anywhere are errors.

## Commands

- **Where it runs.** The root is the nearest folder at or above where necro starts (`-C <dir>` moves the start) that holds `necro.yaml`. The root must be inside a git work tree. A command runs with the root as its working folder, so a script is reached as `uv run --script necro/x.py`.
- **How it's read.** The command is split into words as a POSIX shell would (quotes, backslashes) and run directly: no shell, so no expansion, pipes or redirection. Anything more goes in a script.
- **What it prints.** Each non-empty stdout line is one violation, `path[:line[:col[-endcol]]][:label]`:
  - `path` is relative to the working folder and must name a file in it. With no `line`, the hit is the whole file.
  - `line` and `col` are 1-based; `col` counts Unicode code points; `endcol` is the last column of the span, inclusive.
  - `label`, the rest of the line after a `:` (one leading space dropped), is shown with the hit and is part of its identity in the baseline. `necro grep` prints the matched text there.
  - necro takes positions as printed, so another tool's quirks stay its own: `git grep --column` counts bytes, and with `-o` misplaces the second and later matches on a line.
- **Exit codes.** 0 and 1 are normal (grep exits 1 when nothing matches). Anything else, a line that doesn't parse, or a path that isn't a file is a check error, shown with the last 20 lines of the command's stderr.
- **Runtime.** A command may rely on git and on the repo's own development toolchain; nothing else is guaranteed. If its program isn't on `PATH`, that's a setup error naming the rule and the program. necro puts its own folder first on the command's `PATH`, so `necro grep` and the other [finders](#finders) run as the same necro. Python scripts run best as `uv run --script <file>` with their Python and dependencies declared inline (PEP 723).
- **Time.** A command gets 120 seconds; then necro kills it and reports a check error.

## Finders

necro bundles finders for common searches. A finder is an ordinary command, not a special case: `necro <finder> [options] <args> [-- <pathspec>…]`. Every finder:

- looks at the tracked files matching the pathspecs, read as `git grep` reads them (every tracked file under the working folder when there are none), with paths relative to the working folder; binary files are skipped;
- prints its hits in the format of [Commands](#commands), sorted by path, line and column;
- exits 0 whether or not it found anything, and 2 on a usage error, with `necro: <finder>: <what>` on stderr.

More finders arrive in 0.x releases as adopters need them.

### `necro grep`

`necro grep [--skip-comments <marker>]… <regex> [-- <pathspec>…]`

- `<regex>` uses Rust's `regex` syntax and matches within one line. Every non-empty match is a hit, `path:line:col-endcol: <matched text>`, columns in code points.
- `--skip-comments <marker>` ignores the rest of a line from the first `<marker>` outside a `"…"` or `'…'` string. Give it once per marker (`--skip-comments '#'`, `--skip-comments //`).

## Allows

- An exception is a comment, in the file's own syntax, on the hit's line or the line above: `necro-allow <rule>: <reason>`. necro finds it on the raw line, so any comment style works. A whole-file hit takes an allow on line 1, or line 2 after a `#!` line.
- The reason runs to the line's end or the next `necro-allow`, with a trailing `*/`, `-->` or `;` dropped.
- Two built-in rules keep allows honest, with necro's own wording: `necro/allow-reason` (an allow without a reason) and `necro/unused-allow` (an allow that suppresses nothing, or names no rule). necro finds allows with `git grep` over the tracked files, so an allow in a file no rule covers is reported as unused.

## The baseline

- `necro baseline` writes `necro.baseline` at the root: for every rule, path and label, the count of hits not allowed, as sorted tab-separated lines `rule	path	label	count`. Commit it.
- A run compares each (rule, path, label) count with the baseline. Hits within it are baselined: counted in the summary, not shown. When a count rises above it, every hit of that group is shown and the summary says by how much. Moving code doesn't change the counts, so it doesn't churn the file.
- When counts drop below the baseline, the summary says so; `necro baseline` again keeps the ratchet tight.
- Without the file, nothing is baselined.

## Messages

- **`full`** (default). Each rule's first hit: `error[<rule>]: <message>`, its location, the source line with the span underlined and the label beside it, then `why`, `fix` and the explain command. A repeat: `also at <location>`, its label, and `fix`. Past 4 repeats per rule, the rest are counted per file (`N more in <file>`). Hits sort by rule, path, line and column.
- **The underline.** `col-endcol` sets it; otherwise, when the label appears in the source line at `col`, it spans the label; otherwise one caret. A label that is just the underlined text isn't repeated beside it; a repeat shows its label in parentheses after the location. Tabs show as 4 spaces, the underline moved to match. A whole-file hit shows no source line.
- `why` and `fix` wrap at 88 columns, continuation lines aligned. When `necro` isn't on `PATH`, the explain line adds how to run the installed version.
- **The summary**, after the hits: counts per rule of errors and baselined hits; how far any count rose or fell against the baseline; every allow (rule, location, reason). A clean run with nothing to list prints nothing.
- **`terse`**: one line per shown hit, `path:line:col: rule message` (`path: rule message` for a whole file), nothing else.
- Hits and the summary go to stdout; config, setup and check errors to stderr, as `necro: <kind> error: <where>: <what>`, config errors with `<file>:<line>:<col>: <key path>`.

## CLI

`necro [-C <dir>] [--format full|terse] [--rule <name>]`, `necro [-C <dir>] --explain <rule>`, `necro [-C <dir>] baseline`, `necro <finder> …` ([Finders](#finders)), `necro --version`.

- A run executes every rule's command (or one, with `--rule`), applies allows and the baseline, and prints.
- `--explain <rule>`: the message, `why`, `fix`, `details`, the examples, and the command. An unknown name is exit 2, with the rules listed.
- Exit 0 when nothing fails, 1 when a rule has a hit outside the baseline or an allow is broken, 2 on a config, setup, check or usage error.

## Versioning

- `version` in `necro.yaml` is required. An engine reads the version it implements; another is exit 2, naming the hook rev to move to.
- Breaking (needs a new version after 1.0): removing or renaming a key, changing what a command's output means, changing `terse` or exit codes, a stricter rule that makes a valid config invalid. Not breaking: new optional keys, and changes to `full` layout, which go in the changelog.
